## 已知限制（不是缺陷，是设计如此）

1. **真机（adb）已实测**（v14.2，Quest 3 / Android 14 / toybox 0.8.9 / 216 首真实歌单）：
   `--scan` 正确识别 4 个可用路径，主路径 = `/sdcard/ModData/.../SongCore/CustomLevels`；
   载入 216 首全部解析成功（0 失败）。**仍未实测**的是会改设备数据的两条路
   （复制到设备、设备端删除）和 **MTP 通道**——本机 Quest 的 MTP 没枚举出来
   （`VID_2833` 的 `XRSP`/`COMMLIB`/`Highwind` 三个私有接口缺驱动报 Error，
   但 `ADB Interface` 正常，所以走 adb 不受影响）。
   下次接手可以先做的验证：插上设备后跑 `--scan`，再手工试一次"复制 1 首到设备"。
2. **MTP 模式较慢**：第一版实现是"把整个歌曲目录镜像到本地再解析"，
   上千首会到分钟级；界面会提示。装 adb 后走原生通道快得多。
3. **MTP 无法保留文件时间戳**（Android 端协议限制），所以 MTP 模式取不到 mtime，
   增量扫描会自动退回全量——这是设计如此，不是 bug。
4. **`Android/data` 的 scoped storage**：adb 的 shell 用户通常被豁免，但不同
   Android 版本/Meta 固件松紧不一；现版歌曲目录在 `ModData` 下（不受该限制影响）。
5. **customtkinter 的透明控件不重算底色**：`CTkFrame(fg_color="transparent")` 在外观切换后
   会残留主题默认深灰（实测出一个"标题栏黑块"）。**新增容器时请显式给 `T["BG_CARD"]`**，
   不要用 `"transparent"`；`ui_songlist.py` 的 `_redraw_canvases()` 是兜底补丁。
6. **沙箱里不能用 `tempfile.mkstemp`**（本机环境会阻塞/被拒），`storage.atomic_write_text` 已避开；
   写临时文件请用 `tests/_paths.py` 的 `sandbox()`。
7. **`.pycache__` 会骗人**：改完 `tests/fixtures/fakeadb/fake_adb.py` 后必须清缓存，
   否则 Python 继续执行旧字节码（我踩过一次，排查了半小时）。`run_all.py` 每组前会自动清。
8. **`songlist` 组有一条对机器负载敏感的性能断言**（"6 次击键总耗时 < 1.5 s"，
   `tests/smoke_songlist.py:297`）。在同时跑 `mtp` 组或机器忙碌时**偶发失败**——
   实测同一份代码连跑两次就恢复正常。如果它单独跑通过、在全量里偶发失败，
   先重跑确认，不要急着改代码；要彻底解决就把该阈值改成相对值（例如"单次过滤 < 200ms"）。
9. **已知小瑕疵（不影响功能）**：`tests/screenshot.py` 在最后一张"设备选择器"截图时

## 踩过的坑（第 10–55 条）

> **全文档连续编号 1–54**：第 1–9 条在上面的「已知限制」里，本节从第 10 条接续。
> 新增一条时取当前最大编号 +1，**不许重复、不许跳号**。

10. **"组数全绿"不等于没问题**（v14.1 的血泪教训）：v14.0 交付时 8 组全绿，
    但里面藏着 4 个真实缺陷 —— 盘符探测整条失效、列宽保存失败反而崩、
    窗口可能开成 200×200、同一个常量两份值不一样。**全都落在测试没覆盖的分支上**。
    所以改完"设备探测 / 异常处理分支 / 尺寸夹取"这类平时走不到的路径，
    必须补一条断言，并用 `git stash` 验证"回退源码后它确实会失败"。
    > 后来这条被验证了两次：v15.9 的跨页选择时序问题、v16.2 的自动收起阈值问题，
    > **都是"单独跑绿、混跑才红"**，只跑单个脚本根本发现不了。
11. **同一个常量别写两份**：v14.0 的 `WINDOW_SIZE` / `MIN_SIZE` 在 `constants.py`
    和 `app.py` 各有一份且**值不一样**（`1500x950`/`(1280,820)` vs `1620x1000`/`(1240,780)`），
    `app.py` 那份才生效，而 `_initial_geometry()` 里还硬编码了第三份 `1620, 1000`；
    版本号也在 `constants.py` 与 `__init__.py` 各写一遍。写测试时引用错那一份，
    会得出"修复无效"的错误结论（实际踩过）。现在这些都只有 `constants.py` 一份。
12. **`tests/e2e_gui.py` 会污染真实的 `settings.json`**：它故意验证"数据目录 = 程序目录"，
    所以没走 `sandbox()`，关闭时会把测试窗口的几何（实测是 `200x200+470+200`）
    写进真实的 `settings.json`。v14.1 给窗口尺寸加了最小尺寸下限，不会再开出 200×200
    的窗口，但**每次跑完测试，用户的窗口尺寸记忆会被覆盖**。要彻底解决就让该测试
    把设置写进沙箱路径。
13. **`bulk_read_files` 千万不能"按目录分组"**（v14.0 就是这么写的，v14.2 修的）：
    Beat Saber 是"一首歌一个文件夹"，每个 `info.dat` 都在不同目录里，按目录分组
    就退化成"每首歌一次 adb 往返"。真机 Quest 3 / 216 首实测：
    **78 ms/首 → 整库 18.2 秒**；改成"一次 `tar -cf - -C / <根相对路径>...`"后
    **2.66 ms/首 → 0.57 秒（31.7 倍）**。`e2e_adb.py` 里有一条断言守着它
    （"批量读只发 1 次 adb 调用"）。
14. **`adb exec-out` 不转发 stdin**：想用 `tar -T -` 从 stdin 传文件列表会**一直挂住**
    直到超时（实测）。所以只能走命令行，并按字节预算分片。
    分片上限来自 **Windows 而不是 Android**：`CreateProcess` 命令行上限 32767 字符，
    超了抛 `WinError 206`（实测 32 KB 正常、64 KB 复现），见 `_BULK_COMMAND_BUDGET`。
15. **`/sdcard` 是符号链接，`find` 从它出发返回 0 行**：真机上 `/sdcard -> /storage/self/primary`，
    toybox `find /sdcard ...`（加 `-H` 也一样）**一个结果都没有**。v14.0 的设备探测兜底
    正是这么写的，等于从来没生效过。要搜就 `cd /sdcard && find . ...`（再补回根前缀）
    或从 `/storage/emulated/0` 起搜。**注意假 adb 把两个根都映射到设备根，
    所以它复现不了这个坑**——只能靠真机验证。
16. **`adb push` 在 Windows 上处理非 ASCII 路径有 bug（v14.3 修的 P0）**：
    adb.exe 会**从本地路径自己推导**设备上的目标名，而**路径里每有一个非 ASCII 字符，
    设备上的名字就被截掉 1.5 个字符** ——
    `…\音乐\www.vrmoo.net_1` → `www.vrmoo.ne`；6 个中文时 `www.vrmoo.net_1` → `www.vr`。
    纯 ASCII 路径则完全正常（实测到 221 字符都没问题），所以这是编码问题不是长度问题。
    两个后果：歌曲落在错误名字下（随即报"复制后未找到目标目录"）；
    截断落在多字节字符中间会产生**非法 UTF-8 文件名**，那种名字在 Android FUSE 上
    **删不掉**（rm/mv/find -delete/rmdir/inode/MediaStore 全部失效，只能重启设备清掉）。
    **修法**：本地路径含非 ASCII 时先复制到纯 ASCII 暂存目录 → push → `adb shell mv` 改真名。
    关键线索是 **`adb shell` 通道处理中文完全正常**，只有 `adb push` 不行；
    所以 `AdbBridge.rename()` 必须走 shell，不要用 push 顺便起名字。
    **假 adb 是 Python 写的、复现不了这个 bug**，回归测试守的是"机制"
    （push 的 basename 必须纯 ASCII + 随后必须发 mv），真机行为只能靠 `e2e_device_real.py`。
17. **重启 Quest 会让外置存储变成 `RUNNING_LOCKED`**：重启后 `/sdcard` 直接不存在，
    必须**戴上头显解锁**才会挂载（数据没丢，是 Android 的用户存储加密）。
    用 `adb reboot` 清异常残留之前先想清楚这一点。
    （另：**重启并不能清掉非法 UTF-8 名的残留** —— 实测重启 + 解锁后它还在。
    那种名字在 Android FUSE 上确实删不掉，`adb root` 在零售版也不可用。）
18. **真机 toybox 的 `find -printf '%y'` 是坏的（v14.4 修的 P0）**：
    Quest 3 / Android 14 / toybox 0.8.9 上实测 ——
    `'%y\n'` 单独用输出 **0 行**；与别的格式符组合时**整个输出被截成 1 行**
    （`%f` / `%p` / `%T@` / `%s` 单独或两两组合都正常，**沾上 `%y` 就坏**）。
    `AdbFS.list_files()` 原先用的正是 `'%f\t%T@\t%y\n'`，于是**每个目录只返回 1 个文件**；
    又因为结果非空，那条"为空才退回 ls"的兜底永远不触发 —— 静默截断。
    表现是 **Quest 歌曲封面随机不显示**（`SongFS.cover_name()` 依赖它）。
    现在 `list_files` 固定用 `ls -1p`，并且**假 adb 已忠实模拟这个 `%y` 缺陷**，
    所以回归测试有区分度（改回 `find -printf` 就会红）。
    **这类"设备端命令本身有问题"的坑，离线测试默认发现不了** —— 假 adb 是我们自己写的，
    它实现得"太正确"反而会掩盖真机缺陷。真机验证不可替代。
19. **"写好了但没人调用"是本项目的高发缺陷（已经 8 次了）**：
    tar 分组退化、兜底 find、`%y`、增量扫描（载入从不落库）、`prune_meta`（从未调用
    且 `keep_names` 方向反了）、CopyHere 的源传错、`_missing_side`（属性名写错）、
    `delete_missing_song`（从未调用且方向反了）。
    **接手后请定期做一次"死代码/未被调用"体检**（v14.7 就是这么查出两个真缺陷的）：
    ```python
    # 列出产品代码里"定义了但全仓零调用"的函数/方法
    import ast, pathlib, re
    prod = list(pathlib.Path("quest_tool").rglob("*.py")) + [pathlib.Path("main.py")]
    files = [p for p in prod + list(pathlib.Path("tests").rglob("*.py")) if p.is_file()]
    srcs = {p: p.read_text(encoding="utf-8") for p in files}
    for p in prod:
        for node in ast.walk(ast.parse(srcs[p])):
            if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
                n = node.name
                hits = sum(len(re.findall(rf"\b{n}\b", s)) - (1 if q == p else 0)
                           for q, s in srcs.items())
                if hits <= 0 and n not in ("main", "__init__", "__enter__", "__exit__"):
                    print(f"{p}:{node.lineno} {n}")
    ```
    查到零调用后**先判断它是"纯遗留"还是"本该被调用"** —— v14.7 那 16 个里就有 2 个是后者。
20. **复制后必须校验"文件数 + 总字节"，不能只看目录在不在（v14.5 补的）**：
    v14.3/v14.4 那两个"静默传坏"都属于这一类。设备端用
    `find <dir> -type f -printf '%s\n'`（真机实测与本地逐字节一致；
    **`du -sk` 是块对齐的，会差几千字节，不能用**）。
    `tests/e2e_adb.py` 有 `FAKE_ADB_PUSH_SKIP` 故障注入，能端到端测到"少传了文件"。
    MTP 只能比顶层文件数（Shell 的"大小"列是四舍五入后的字符串）。
21. **`try/except Exception` + 只记 debug 日志 = 缺陷隐身衣**（v14.7 的教训）：
    `set_view_mode` 把每一列的刷新包在 `try/except Exception` 里只记 `logger.debug`，
    于是 `_missing_side` 的 `AttributeError` 被完全吞掉，表现为"封面墙缺失列永远是空的"
    —— 不崩、不报错、也没人知道。**吞异常时至少要 `logger.warning`**，
    并且**别把"整块功能"包进一个宽泛的 except**。
22. **CopyHere 复制的是"源目录里的全部条目"，所以必须用 `-Only` 限定（v14.6 修的 P0）**：
    `shell_copy.ps1` 做的是 `$destFolder.CopyHere($sourceFolder.Items(), ...)`。
    想复制"某一首歌"时，**源必须传歌曲库目录 + `-Only <歌曲名>`**：
      * 只传歌曲库目录 → **整个歌库**都被推过去（v14.5 之前就是这样，
        复制一首歌 = 把用户上千首全传一遍，而且 `replace=True` 还会把设备上同名歌曲
        逐个改名挪开重传）；
      * 只传歌曲目录 → 它的**内容**被平铺进目标（`info.dat` 散落在 CustomLevels 根下）。
    三个调用点（`copy_into` / `copy_out` / `_pull_one`）都必须带 `-Only`。
    `e2e_mtp.py` 第 5 节有断言守着"设备上不能多出源目录的兄弟条目"。
23. **改 `shell_*.ps1` 后必须补回 UTF-8 BOM**：编辑工具会**静默去掉 BOM**，
    而 PowerShell 5.1 读无 BOM 的 UTF-8 会按 GBK 解码 → 中文路径/提示全乱码 → COM 调用失败。
    v14.6 就踩了一次，被 `tests/static_check.py` 当场抓住（所以那条检查别删）。
    补 BOM：`[System.IO.File]::WriteAllBytes($p, [byte[]](0xEF,0xBB,0xBF) + [System.IO.File]::ReadAllBytes($p))`
24. **MTP 镜像现在是增量的**：用 Shell 枚举设备目录（只列名字，~1.3 秒）比对
    "本地缺的 / 修改日期变了的 / 设备上已删的"。清单存在 `<镜像>.manifest.json`
    （放镜像目录**外面**，否则会被当成一首歌）。
    **保守兜底**：设备枚举不到歌曲但镜像里有时，判定为"枚举出问题"而**不动镜像** ——
    绝不能因为一次枚举失败就删掉用户的镜像数据。
25. **`mtp` 组会真的起 PowerShell + COM**（每次约 1.3 秒），所以跑得比别的组慢。
    这是必要的：只有真跑 COM 才能测到 CopyHere 的语义（本次 P0 就是这么发现的）。
26. **"参数是源，但要按目标算"这类错位很难看出来（v14.8 的教训）**：
    `_estimate_copy(source_fs, songs)` 里用 `fs.location.kind` 选速率，
    而 `fs` 是**源** —— 于是"本地 → Quest"按本地磁盘 150 MB/s 估算，
    把 9 秒说成 1 秒（真机实测 adb 17.4 MB/s）。
    **凡是"速率 / 容量 / 瓶颈"这类量，先问清楚它属于哪一端**；
    现在用 `_channel_key(source_kind, target_kind)` 明确表达"瓶颈是设备那条通道"。
    另外**别写死速率**：`transfer_rates` 会用每次真实传输做 EMA 自我修正
    （USB 2/3、线材、无线 adb 的差异太大了）。
27. **"设置了但没人读"也是同一类问题（v14.9 审计出来的）**：
    15 个 `Settings` 字段里 **5 个从未被读取** ——
    `copy_overwrite` / `quest_source` **只有定义、没有任何实现**（没界面也没逻辑）；
    `scan_state` 已被 v14.5 的数据库缓存取代；`recent_local` / `recent_quest`
    更微妙：**应用一直在写（`remember()`），却从来没人读**，"最近路径"是个半成品。
    **接手后可以顺手做这个审计**：对每个 `Settings` 字段，
    `grep -rn "settings\.<字段>" quest_tool/` 看有没有人读。
28. **后台线程碰 UI 有静态检查兜着了（v14.9）**：`static_check.py` 第 4 项会扫
    所有 `self.tasks.submit(<名字>)` 提交的函数体，发现 `self.toast.` / `self.root.` /
    `self.list_*` 等就报错。**想让后台任务弹通知，发一条 `"toast"` 消息**
    （`self.tasks.emit("toast", "", -1, payload={"level":..., "text":..., "detail":...})`），
    由主线程 `_pump_queue()` 来弹 —— 别在 worker 里直接调 `self.toast.*`。
29. **静态检查现在也扫 `tests/`**（排除 `tests/archive/`）：测试写坏了同样是问题。

37. **第三方库"按扩展名猜格式"是个隐形开关，`.egg` 这类私有扩展名必然踩**。
    miniaudio 的 `get_file_info(路径)` / `decode_file(路径)` 在 `.egg` 上**一律失败**
    （`DecodeError: unsupported file format`），而文件头明明是 `OggS\x00\x02`。
    **判定方法是"复制成 .ogg 再试"** —— 立刻成功就证明是扩展名而非内容的问题。
    **解法是绕开路径 API 走字节 API**：`miniaudio.decode(data, output_format=..., nchannels=2, sample_rate=44100)`。
    教训：遇到"格式不支持"先别信，先验**文件头**（`read_bytes()[:4]`），
    再验**是不是路径/扩展名/元数据在作祟**（换名、换 API、换入口）。
    同类陷阱：把 `.egg` 当成音源给任何"按后缀分发解码器"的库，都会这样。

38. **"文档说的是意图，代码做的可能是另一回事"——而文档会替错误打掩护。**
    v16.9 修的这个缺陷，是**文档与实现不符却看起来完全一致**：

    * 类文档写"用 `stream_memory` **边解边喂**，所以①起步快②内存小③停止干净"；
    * 代码前半段 `data = audio_file.read_bytes()` → `ma.decode(整曲)` → 再切前 30 秒；
    * 后半段**确实**把生成器交给了 `PlaybackDevice`。

    每一句话都能对上"有那么个生成器"，但**为了听 30 秒把 369 秒整曲全解进了内存**：
    峰值 66.0 MB（源文件的 4.8 倍）、580 ms。改成真流式后 **13.7 MB / 72 ms**。

    **怎么发现**：不是读代码读出来的，是**量出来的** ——
    用 `tracemalloc` 给"最大的一首歌"测峰值内存，一眼就看出 66 MB 不正常
    （源文件才 13.66 MB）。**症状是"能听、也没崩"，没人会去查。**

    **教训**：
    - 凡文档里出现"流式 / 增量 / 懒加载 / 边…边…"，**都要有对应的量化断言**，
      否则它只是作者的愿望。本项目这类"写了但没生效"已累计 **10 次**（见第 19 条）。
    - 性能缺陷不会报错。**给"最大值"设个度量**（最大文件 / 最多歌曲 / 最长路径），
      定期量一遍，比读代码有效。
    - **衡量要公平**：第一版微基准把 `read_bytes()` 算进了新方案、却没算进旧方案，
      得出"快 8.9×";重新用同一份 `data` 做基线才是诚实的 **8.0×**。
      写进文档的数字必须是同一口径下测的。

39. **改"限长/截断"类逻辑后，必须逐样本比对输出，不能只断言时长。**    v16.9 把播放从"整曲解码后切片"改成流式，最容易悄悄改变音频内容
    （少一帧、多一帧、边界算错）。`tests/smoke_audio.py` §9.2 的做法是：
    用旧实现（`decode_preview`）算出参考片段，再 `array` 逐样本比较，
    要求**样本数一致且每个样本相等**。只断言"时长约等于 2 秒"是看不出来的
    —— 差 1 帧只有 0.00002 秒，任何容差都放过。

    同样地，"资源有没有被释放"也不能靠"应该有吧"：
    §9.7/§9.8 用一个转发包装对象记录 `close()` 次数，
    证明连续切 20 首时 **20/20** 都关了（修复前 0/20）。
    注意 **`generator.close` 是只读的，不能 monkeypatch**，必须包装。

40. **UI 问题要量化成数字，否则改不动也验不了。** v17.1 修"预览图后面特别大的黑边"时，

41. **同进程里建两个 `ctk.CTk()` 根会制造"假缺陷"。** v17.1 排查详情栏封面时报

42. **"点了没反应"几乎总是"回调里抛异常被 Tk 吞掉"，而这类异常**能**静态查出来。**

43. **"取不到 / 传错类型"比"传错值"更会骗人 —— 因为会被 `except` 兜住变成"什么都没发生"。**
    v17.2 用户说"试听没用"，而音频模块单测 66 项全绿。拿真曲库一跑才发现
    **85 首里 83 首**失败，且**一声不响**：`_find_audio_file()` 返回 `str`，
    `decode_preview()` 内部用 `source.name` → `AttributeError` → 被 `except` 兜住 → 返回 `None`。
    教训：① **"能兜住的异常"要分级** —— 音视频这类"降级即静默"的地方，
    失败必须留下**可数的痕迹**（哪怕只是计数/日志级 warning），否则测试和用户都发现不了；
    ② **测试要用真样本**，我原来的假 WAV 是 `Path`，真曲库那条路径传的是 `str`，
    两者形状不同 —— "自造数据太干净"会掩盖真实调用链上的类型错误
    （这和"假 adb 太正确"是同一类坑，见第 22 条）。

44. **"只在自己退出时保存"等于"经常不保存"。** v17.2 用户报"路径重启就没了"。
    原先路径只在 `on_close()` 写盘 —— 崩溃、被强杀、任务管理器结束都会丢；
    而成功路径的 `remember()` 又在**后台线程**里，用户看到歌单出来了就以为存下了。
    教训：**用户手动做过的、明确表达过的意图（输入了路径、选了目录），要在他松手那一刻就落盘**，
    不要攒到退出。判断标准很简单：**如果程序在下一秒被 `taskkill`，这条信息该不该在？**
    该在，就立刻写。

45. **属性写成方法调用不会报"不存在"，只会报 `TypeError: 'float' object is not callable` —— 而它落在回调线程里时，看起来像"卡死"。**
    v17.3 给试听加进度条，`PreviewPlayer.start_offset` 是 `@property`，测试里写成
    `player.start_offset()`。真实表现不是报错退出，而是：那个异常发生在
    **音频回调线程**里，主线程随后在解释器退出阶段等它 → **整条命令不返回，
    只能 `job_kill`**（我一度误判成"`@property` 被访问时执行了阻塞逻辑"）。
    教训：① 排查"卡住"先用 `Start-Process -PassThru` + `Start-Sleep` + `$p.HasExited`
    判定是不是真挂，再看 **stderr** —— 异常往往早就打出来了，只是没到 stdout；
    ② **凡是 daemon 线程里可能抛异常的路径，都要在源头自己接住并记日志**，
    否则"后台炸了"会伪装成"前台卡了"；③ 命名上区分"值"和"动作"：
    属性不加 `get_`、方法必带动词，是防这类笔误的第一道防线。

46. **"同步关闭音频设备"看起来无害，实测每次 100~600 ms，而且是卡在界面线程上。**
    `device.stop()` 内部要 join 音频回调线程，实测耗时≈ `buffersize_msec` 的
    **2.5 倍**（200ms → 约 600ms，60ms → 约 107ms）。试听的"停止/切歌/拖动起点"
    全都走这条路 → 用户每次操作卡半秒。
    修法：`_device` 在锁里**原子摘走**，关停丢给后台 `daemon` 线程
    （实测 **600ms → 0.5ms**）。注意两条铁律：**不能在音频回调线程里调
    `device.stop()`**（自锁死，实测挂住 2 分钟）；**不能让非 daemon 线程留着**，
    否则解释器退不出来。
    教训：**"这次操作要多久"是能测的** —— 凡是界面线程上会调用外部设备/系统 API
    的路径，都应该有一个"最坏耗时"的实测数字，而不是"应该很快吧"。
    （写这条时发现 `_close_device()` 的 docstring 早就写着"在独立线程里关掉"，
    但函数体一直是同步调用 —— 又是第 38 条那种"文档替错误打掩护"。）

47. **"区分度不够"是个能被测试抓住的问题，前提是先把它变成数字。**
    v17.4 用户说"UI 的区分不够明显、每个功能要区分开来"。这种要求听起来只能靠审美，
    但拆开看它其实是三条**可断言**的约束：
    ① 三列的语义色**两两不同**（改回同一个值就失败）；
    ② 三列的图标**两两不同**（色盲用户靠它区分，所以图标是**必需**的，不是装饰）；
    ③ 语义要对得上（本地=主色、设备=INFO、缺的=WARNING）。

    做法：把三列的"身份"收进 `app_common.COLUMN_IDENTITIES` **一处定义**
    （`ColumnIdentity(accent, icon)`），`app.py` / `ui_songlist.py` / `ui_coverwall.py`
    都从这里取。**为什么必须集中**：这三样要同时出现在列表标题栏、封面墙标题栏、
    空状态提示三处，各写一遍必然漂移 —— 本项目已经出现过"同一份东西两处定义、
    只改了一处"（`BACKUP_SUFFIX`、`WINDOW_SIZE`、`PREVIEW_SECONDS_CHOICES` 都中过）。

    颜色按**副作用**分配而不是按好看：蓝=只读、紫=只改视图、绿=真的写磁盘、
    红=不可逆。用户扫一眼颜色就知道哪颗按钮会动文件。

48. **加一个 UI 元素会把版式撑坏，而且只有版式测试会发现。**
    v17.4 把操作按钮从 3 组加到 4 组（横排），`tests/scaling_check.py` 当场报：

        [FAIL] [1.0] 内容装得下（不被裁切）  -> 需要 1834x710，实际 1700x950

    四个组一行要 **1834px**，而基准窗口 1700px —— 超出的部分会被裁掉。
    改成 **2×2 grid** 后需要宽度降到 **1603px**。

    教训：① **横向堆叠的控件数量是有上限的**，加之前先量一下
    `root.winfo_reqwidth()` 对比窗口宽度；② 这类缺陷的表现是"按钮被切掉一半"，
    用户会以为是显示 bug 而不会想到版式，**没有 `scaling_check.py` 就只能等用户报**；
    ③ 修法是"换行"而不是"把窗口改宽" —— 窗口宽度是用户的，不该由我们的按钮数量决定。

49. **"没有重叠、没有裁切"不等于"版式对" —— 控件被挤扁时它一声不吭。**
    v17.4 把操作按钮改成四个分组卡片交付后，用户立刻报"很严重的问题"：底部四个分组
    各被撑成 772x212 的方块（共 432px），把三个歌曲列表挤到 **212px**，
    表格区只剩 **28px —— 一行歌都显示不出来**。

    **根因**：`CTkFrame` 只给了 `width` 就调 `pack_propagate(False)`，
    而它的**默认高度是 200**；关掉"按子件收缩"之后 200 被当成真实高度用了。
    **`pack_propagate(False)` / `grid_propagate(False)` 之后宽高必须都给全。**

    **为什么 `scaling_check.py` 原有 4 条断言全过了**：
    「内容装得下」看的是请求高度 —— 没超标；「控件不重叠」—— 列表只是**变矮**，
    没压到别人。**被挤扁的控件不报错、不重叠，只是变小**，这是最难被发现的一种坏法。
    更巧的是 `ttk.Treeview` 被刻意设成 `height=1`（`ui_songlist.py:328` 有注释），
    它的请求高度恒为一行 28px，**恰好和被挤扁的结果一模一样**，于是请求高度这条
    判据对这个 bug 完全失效。

    **新增判据**：不问"父容器装不装得下"，直接量**受害控件自己的可用尺寸** ——
    `(tree.winfo_height() - 4) / row_height >= 8` 行。改坏后 2.7 行当场报错。

    **推广**：凡"尺寸由剩余空间决定"的控件（`weight=1` 的表格、滚动区、画布、
    带 `expand=True` 的容器），判据都要落到它自己身上。加新控件后要问的不是
    "会不会溢出"，而是"**它挤掉了谁的空间**"。

50. **"卡死"最难受的地方是日志里什么都看不到 —— 所以诊断设施本身必须是可测的。**
    用户报「使用时貌似会卡死」。真凶查到了：**界面线程同步跑 adb 命令，
    插着非 Quest 的安卓设备时冻结 5.2 秒**（设备探测已挪到后台线程）。
    但要查到它，前提是日志能说出**卡在哪一步** —— 而原来日志里"最后一条 INFO"
    之后就是一片空白，与"没有卡死"**完全无法区分**。
    新增 `quest_tool/diagnostics.py`：主线程心跳看门狗（`TICK_SECONDS = 0.05`、
    `STALL_FACTOR = 5.0`，判据 0.25 秒）、`slow()` 上下文管理器（`SLOW_SECONDS = 0.8`）、
    `sys.excepthook` + `threading.excepthook` 接管。**这三样都由
    `tests/smoke_diagnostics.py` 专门守着**（34 条）—— 诊断代码坏掉的表现恰恰是
    "日志里什么都没写"，不测就永远发现不了。

    **两个反直觉的设计**：
    ① **必须区分"是不是界面线程"** —— 同样耗时 1 秒，跑在界面线程上才叫卡死，
    跑在 worker 上只是慢。不区分的话，看日志的人会去优化一条不影响体验的路径。
    ② **卡顿发生时 `current` 已经是空的** —— 界面线程冻结时心跳回调排在它后面，
    等心跳醒过来操作早就结束了，于是日志只能说"当时没有登记任何操作"，
    **恰好丢掉唯一有用的线索**。所以要保留"刚跑完的操作"（`KEEP_LAST_SECONDS = 5.0`），
    日志才能说「多半卡在刚跑完的『建立主界面』上」。

51. **同一个类里写了两个同名方法，Python 不报错，先定义的那个直接消失。**
    加诊断对话框时我**又写了一个 `show_diagnostics`** —— 而类里早有一个同名的
    （环境自检信息）。类体里**后定义的覆盖先定义的**，新写的那个变成死代码，
    **不报任何错、静态检查 7 项也全都过**（第 7 项只查"调用了不存在的方法"，
    管不了"方法被同名覆盖"）。
    这是"写了但没生效"缺陷家族的第 11 个成员，也是最隐蔽的一个：
    前面 10 个是**没人调用**，这个是**被同名方法遮住**。
    **守它的办法**：AST 取主类的 `FunctionDef` 名字，断言没有重复
    （已加进 `tests/smoke_features.py` §6）。**加 UI 元素、加对话框时最容易撞上**。

52. **改模块全局常量，改不动函数默认参数 —— 默认值在定义时就绑定了。**
    写 `slow()` 的测试时我想"把 `SLOW_SECONDS` 临时改成 0.01 来制造一次慢操作"，
    结果 `with diagnostics.slow("测试用慢操作")` **什么都没记**。
    原因：签名是 `def slow(what, *, seconds=SLOW_SECONDS)`，默认值在**函数定义时**
    就求值绑定了，之后再改模块全局对它毫无影响。
    **正确做法是把阈值显式传进去**（`slow("x", seconds=0.01)`）。
    **判别方法**：测试"改了全局却没生效"时，先看它是不是被当作**默认参数**用掉了。
    同类陷阱：可变默认参数、闭包捕获的是变量而非值。

53. **「视图」和「曲库」在代码里长得一模一样，混起来就是 `KeyError`。**
    三列里只有两列是**真实曲库**（`libraries` 里就 `local` / `quest` 两项），
    第三列「缺失」是前两者的**差集视图** —— 它没有自己的 `fs`、没有自己的 `meta`，
    真正拥有那些歌的是 `missing_side` 指的那一侧。

    v17.7 给列表加筛选档位时，`_make_item(kind, folder)` 直接 `self.libraries[kind]` 取库，
    于是 `kind == "missing"` 必然 `KeyError: 'missing'`，**「对比」整条链路当场断掉**。

    **为什么藏得住**：`compare` 是按钮回调，异常被 Tk 的命令分发吞掉 ——
    用户看到的是"点了对比没反应"（这与本项目此前 3 次「点了没反应」同源）。

    **修法**是加一个显式映射 `_sample_kind(kind)`，把视图名翻成真实曲库名，
    让 `_make_item` / `_ratings_for` / `_refresh_wall` 统一走它。
    **判别方法**：凡是 `libraries[name]` / `dict[name]` 这种按名字取容器的地方，
    先问一句"这个名字**一定有对应的那份数据**吗，还是它其实是个视图？"

    顺带把散在各处的 `kind if kind != "missing" else self.missing_side` 收编 ——
    **同一个映射写三遍，第三遍必然写错**。

54. **"界面一片空白"和"界面压根没建出来"要分开验，否则会误判成版式问题。**
    v17.7 重设版式后我用自绘 PNG + 视觉模型看效果，模型报告"中下部约 40% 是纯白空地"。
    但几何 dump 显示那块区域被列表（到 y=854）和操作栏（y=872）占满了 ——
    **模型对结构的判断不可信**（它还把纯色块说成"2×2 卡片网格"）。

    **正确做法**：视觉模型只用来确认"某个区域是什么颜色/在哪"，
    "这块空间归谁"必须回到 `winfo_geometry` / `winfo_reqwidth` 的数字上。
    本项目的 `tests/.tmp_geom*.py` 那套 dump 就是为这个准备的。

55. **"零调用"的判据必须包含别名导入 —— 否则删掉的是活代码，而静态检查抓不到。**
    v17.8 精简时我用 AST 统计"零调用函数"，把 `audio.find_file` 判为死代码删掉了。
    **它是活的**：`app_detail.py` 用 `from .audio import find_file as audio_find_file` 导入并在第 490 行调用。
    **漏判原因**：扫描器只收集「调用名 + 变量/属性引用 + 字符串字面量」，
    **没收集 `ImportFrom` / `Import` 的导入名**，别名导入完全看不见。

    **最要命的一点**：`tests/static_check.py` 的 **7 项全都通过** —— 它只做 AST 判断、不真的 import 模块，
    所以看不到运行时的导入错误。**只有真跑测试**才炸出
    `ImportError: cannot import name 'find_file' from 'quest_tool.audio'`。

    **判别方法**：删任何东西之前，先在**全仓 grep 该名字**（含 `import ... as` 这种别名形式），
    再跑一次**真测试**（不是静态检查）。**静态检查再全也替代不了跑测试。**

56. **"我加了优化所以变快了"——这是最容易被自己骗过去的一类结论，必须量总账。**
    v17.9 做启动优化时，我先测到"第一个 emoji label 要 277 ms"，于是加了
    `theme.warm_emoji_font()` 预热。**局部数字非常漂亮**：
    `_build_appbar` 从 445 ms 降到 147 ms（−67%）。

    但我一度在代码注释里写了"`__init__` 1463 → 1298 ms，约 160 ms"——
    **这个数字复现不出来**。用严格方法（同臂交替采样、独立进程、取中位数）重测：

    | 阶段 | 不预热 | 预热后 | 差 |
    |---|---|---|---|
    | `_build_ui` | 1220 ms | 906 ms | −314 ms |
    | 建界面之前（含预热自身） | 232 ms | 601 ms | +369 ms |
    | `__init__` 总计 | 1452 ms | 1512 ms | **+60 ms（反而略慢）** |

    **真相**：预热不是"消掉"成本，而是**把成本搬家** ——
    从"建标题时"挪到"还没建任何控件时"。总耗时**没有**改善。

    **三条教训**：
    * 优化必须报**总账**，不能只报自己改的那一段。局部 −300 ms 与总量 ±0 可以同时成立。
    * **同进程里做 A/B 会骗人**：Tk 的字体回退是**进程级一次性**成本，
      同一进程跑第二次早就预热好了 —— 我最初的同进程 A/B 得出"两边都是 20 ms"，
      差点据此判定优化无效。必须**独立进程 + 交替采样 + 中位数**。
    * 本机**测不出真正的首帧延迟**（窗口 `withdraw()`，绘制被推迟到 `deiconify()`，
      `update_idletasks` 恒为 0.0 ms）。**测不到就说测不到**，
      别把"建界面快了"悄悄转述成"用户等得少了"。

    已把这个度量固化成 `tests/perf_startup.py`：它只断言
    "`_build_appbar` 下降 ≥ 120 ms"（预热是否还兑现），
    **不**断言总耗时更快 —— 因为总耗时本来就没变快。

57. **字体回退是"按码点分别查找"的，所以预热一个 emoji 不够。**
    承接上一条：我第一版 `EMOJI_WARMUP_TEXT` 只写了 `"🎵"`。实测 13 个界面图标
    挨个建 label 的总耗时：**不预热 414.6 ms ｜ 只预热 🎵 123.7 ms ｜ 预热全部 54.7 ms**。
    因为 💻(U+1F4BB)、🥽(U+1F97D)、🔌(U+1F50C)、📥(U+1F4E5)、🗑(U+1F5D1)
    各自首次都要 ~265 ms —— **每个不同的 emoji 都要单独付一次**。
    （只有 ⚠️ 便宜些：110 ms，因为它是 BMP 码点 + 变体选择符 U+FE0F。）

    **判别方法**：做"预热 / 缓存 / 懒加载"这类优化时，
    先确认缓存的**键**到底是什么粒度（这里是"码点"，不是"字体"，也不是"某个控件"），
    再决定要预热哪些。想当然地以为"预热一个就等于预热一类"会白干一半。

58. **`print` 里的非 ASCII 字符能让"全通过的检查"返回失败退出码。**
    `tests/static_check.py` 末行是 `print("...全部通过 ✔")`，`✔`(U+2714) 不在 GBK 里。
    在中文 Windows 控制台（代码页 936）直接跑就会抛
    `UnicodeEncodeError: 'gbk' codec can't encode character '\u2714'`，
    于是 **7 项检查全部 PASS，进程退出码却是 1**。

    这个坑平时被掩盖着：`tests/run_all.py` 给子进程注入了 `PYTHONUTF8=1`，
    所以只有**单独直接跑**时才暴露 —— 而"改完先跑 static_check"正是日常动作。

    **比漏检更坏**：退出码 1 会让 CI / 批处理 / 下一个 AI 判定"检查没过"，
    去修一个不存在的问题，并从此不信任红灯。

    **修法**：模块顶部给 `sys.stdout` / `sys.stderr` 加 `errors="replace"`
    （只在真不可编码时才降级成 `?`，正常 UTF-8 控制台输出不变）。
    **判别方法**：凡是脚本的退出码会被别人当判据，就要保证
    "输出编码"不可能影响"退出码"。
