# 改进说明（原版 → 重构版 v14.0）

* 原版：`源代码_原始版.py`（单文件 4155 行）
* 新版：`main.py` + `quest_tool/`（17 个模块）
* 所有结论都来自本机实测（Python 3.13.2 / customtkinter 5.2.2 / Pillow 11.1.0 / sqlite 3.45.3），
  验证脚本在 `_review/`，一键运行：`python _review/run_all.py`（7 组，全部通过）。

---

## 一、先说结论：原版有 3 个会**真实丢数据**的缺陷

这些不是"代码风格问题"，是实测能复现的事故：

### 1. 复制时会把源歌曲删掉（P0）

```python
# 原版 2547-2559
if os.path.exists(dst_path):
    shutil.rmtree(dst_path)      # ← 没有校验"源≠目标"
shutil.copytree(src_path, dst_path)
```

当用户把"本地路径"和"Quest 路径"填成**同一个文件夹**时，`dst_path == src_path`，
于是先 `rmtree` 删掉源歌曲、再尝试复制 —— 实测：`before ['Song1'] → after []`，
界面只报"成功 0，失败 1"，用户完全不知道歌被删了。

**新版**：`workers.guard_copy()` 在动手前拦截"源==目标 / 互为父子目录 / 非法名字"，
并给出明确原因。实测所有 6 种危险组合全部被拦。

### 2. 删除可以打到任意路径（P0）

```python
# 原版 2652-2663
shutil.rmtree(base_path)   # base_path = os.path.join(路径变量, 歌名)
```

路径变量为空时 `os.path.join('', 'RelativeSong')` 变成**相对路径**，
实测会删掉"当前工作目录"下同名文件夹。而且整个 `rmtree` 跑在主线程，大目录直接卡死界面。

**新版**：`guard_delete()` 强制"绝对路径 + 必须是歌曲根目录的直接子目录 + 不是盘符根 +
不含分隔符"，删除在后台线程执行，**删除后复查目录是否真的消失**，
设备侧删除再叠一层二次确认（可"以后不再提示"）。

### 3. 界面会假死（P0，性能）

原版给每首歌建 2 个控件放在滚动框里，搜索框每次按键都全量重建：

| 场景 | 原版实测 | 新版实测 |
|---|---|---|
| 渲染 2000 首 | **8001 个 Tk 控件，15.48 秒** | 恒定 42 个控件，只渲染当前页 |
| 1000 首连敲 5 个字符 | **29.82 秒（5.9 秒/键，界面假死）** | 键入 1.5 ms；单次过滤+重画约 12 ms（另有 180 ms 防抖） |
| `set_items(3000)` | — | **4.3~5.5 ms** |

实现方式：`ttk.Treeview` + 分页（默认 100 行/页）+ `trace_add` + 180 ms 防抖。

## 二、其余 P1 缺陷与修复对照

| # | 原版缺陷（含行号） | 现象 | 新版修复 |
|---|---|---|---|
| 1 | 1191 `root.bind("<Delete>")` 全局绑定 | 在**搜索框里按 Delete 也会触发删歌**（实测回调被调用） | Delete 只绑在 Treeview 上并返回 `"break"` |
| 2 | 2410-2421 用未排序列表的下标做高亮 | 排序后**高亮错歌**，据此删除会删错文件（实测应为 Apple，实际高亮 Mango） | 高亮集合存**文件夹名**，与排序/分页/过滤无关 |
| 3 | 914-925 存了 `file_mtime` 却从不比较 | 缓存**从未生效**，每次选中都重新解析 info.dat | 以 `(folder_name, mtime)` 为缓存键，命中直接返回 |
| 4 | 921/954 `encoding='utf-8'` + 窄 except | UTF-8 **BOM** 文件整份失效；**GBK** 文件抛 `UnicodeDecodeError` 逃出 except 打断界面 | `songs.decode_json_bytes()` 依次尝试 utf-8-sig → utf-8 → gbk → big5 → latin-1，绝不抛异常（两种都实测通过） |
| 5 | 254-257/762 `update_song_rating` 不看 rowcount | 恒返回 True，评分"保存成功"但丢失 | UPSERT + 写入后校验；且元数据/用户数据**分表**存储 |
| 6 | 972-986 无 info.dat 的歌曲不建库行 | 这类歌的评分同样丢失 | 无论是否解析成功都写库，缺失用空值表示 |
| 7 | 评分以 `folder_name` 为主键 | 本地与 Quest 的**同名歌曲共用一条评分**，在设备上打分本地也跟着变 | 用户数据以 `(位置标识, folder_name)` 存储，两边独立（实测已验证互不影响） |
| 8 | 11 处工作线程直接 `root.after(...)`（2025/2028/2032/2035/2113/2116/2121/2576/2578/3019/3023） | Tk 非线程安全，高负载下随机崩溃/死锁 | **工作线程只允许 `queue.put()`**，`TaskRunner` + `_pump_queue()` 是唯一 UI 更新入口；任务带 token，旧任务的迟到消息被丢弃 |
| 9 | 3004-3013 `refresh_cache` 删库 + 跨线程重绑 | 竞态，且**静默清空全部评分/评价** | 改为 `PRAGMA`/分表 + `prune_meta()` 只清元数据缓存，用户数据永不触碰 |
| 10 | 1798-1809 用 `GetLogicalDrives + DRIVE_REMOVABLE` 找 Quest | 物理上不可能命中（MTP 无盘符），只会去 U 盘瞎找 | `device.scan_quest()`：盘符 → adb → MTP 三路探测 |
| 11 | 难度解析只覆盖 v2/v3 | v4 的 `difficultyBeatmaps` 读不到；`Expert+` 等别名不归一 | 覆盖 v1/v2/v3/v4，别名归一化，按时长+难度排序输出 |
| 12 | 时长、`_coverImageFilename` 未使用 | 详情里没有时长；封面只能靠猜文件名 | 解析 `duration`；优先用 info.dat 指定的封面文件名 |
| 13 | `setup_logging()` 在 import 时写相对 `logs/` | 打包/换工作目录后日志乱跑或失败；重复调用叠加 handler | 懒初始化 + 轮转日志 + 目录自动回落 |
| 14 | `songs_cache.db` / `settings.json` 写当前工作目录 | 计划任务/双击 bat 启动时文件散落到处 | 统一写程序目录，不可写则回落 `%LOCALAPPDATA%`；设置**原子写** + 损坏自动备份自愈 |
| 15 | 每个方法 `sqlite3.connect/close` | 每首歌一次连接；无 WAL；逐条 commit | 单连接 + WAL + `check_same_thread=False` + 互斥锁 + `executemany` 批量提交 |

## 四、针对 Quest 设备的新能力

原版对 Quest 只有一条（错误的）盘符探测路径，其余全靠用户手工填。新版：

1. **adb 后端**（推荐）：`ls/cat/pull/push`、`find -printf` 一次拿全量 mtime、
   `tar -cf -` 把上千个 `info.dat` 打包成**一个流**批量读回 —— 3000 首从"每首两次往返"降到几次调用。
2. **MTP 后端**（零安装即可用）：用 Shell `Folder.CopyHere()` 把设备歌曲目录镜像到本地再解析。
   读取、复制到设备、复制到本地都能工作；删除被**故意禁用**（MTP 删除无法可靠确认且无回收站）。
   实测：镜像 + 解析 + 单曲复制 + 反向复制全部通过。
3. **自绘设备文件夹选择器**：懒加载目录树（后台线程 + 主线程心跳搬运）、一键跳到 CustomLevels、可手输路径。
4. **路径候选更新**：`ModData/SongCore/CustomLevels` 优先（现版 SongCore 的正确位置），
   兼容 `ModData/SongLoader`、`CustomWIPLevels` 与历史 `Android/data` 路径。
5. **明确的能力告知**：选到 MTP 路径时会说明"会先镜像到本地"；设备断开/未授权时给出可操作的排查步骤，
   而不是抛 `FileNotFoundError`。

细节见 **[`Quest3文件夹选不了_解决方案.md`](Quest3文件夹选不了_解决方案.md)**。

## 六、已知限制（如实说明）

1. **MTP 读写的性能**：第一版实现走 Shell 的 `Folder.CopyHere`，相当于把整个歌曲目录复制一份。
   它比 adb 慢（实测小样本 2 秒级，上千首会到分钟级），所以界面会提示"首次镜像较慢"。
2. **MTP 删除已禁用**：MTP 删除无法可靠确认结果、设备上也没有回收站，因此宁可让用户手动处理。
3. **真机未验证的部分**：本机没有 Quest 也没有 adb，所以
   `askdirectory` 在真机上"点了没反应"的具体表现、真机 adb 路径、MTP 实机目录树
   只能从原理（Tk 源码路径 + 官方 API 语义）和"无设备时的降级行为"两侧验证。
   **代码已按"两种连接方式都可用"设计**，真机复测建议先用 `python -m quest_tool --doctor` 与 `--scan`。
4. **Android 版本差异**：`adb pull /sdcard/Android/data/...` 在 Android 13/14 与 Meta 固件上的
   宽松程度不一致（adb 的 shell 用户通常被豁免，但并非所有版本都如此）；
   现版歌曲目录在 `ModData` 下（不在 `Android/data` 内），不受该限制影响。
5. **MTP 不保留时间戳**：Android 端 MTP 协议无法设置文件时间，镜像后 mtime 会变成复制时间，
   因此 MTP 模式的缓存以镜像内容为准（重扫会重新解析，但不影响正确性）。
