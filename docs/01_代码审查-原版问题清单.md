## 2. P0 阻断级缺陷

### P0-1 复制时源目录 == 目标目录 → 源歌曲被 `rmtree` 永久删除

* **行号**：2547-2559（`copy_missing_background`），触发路径 2458-2470
* **问题代码**：
  ```python
  # 如果目标路径已存在，先删除
  if os.path.exists(dst_path):
      shutil.rmtree(dst_path)          # ← 2548-2550
  shutil.copytree(src_path, dst_path)
  ```
* **原因**：`_copy_missing_songs` 只校验了两个路径各自非空、源路径存在，**从未校验 `source_path != target_path`，也未校验目标是否是源的后代**。当用户把本地/Quest 两个输入框填成同一个目录（手动输入时非常常见），`dst_path == src_path`，于是先把自己删掉，再复制一个已经不存在的目录 → 歌曲永久消失。文件对话框允许选同一个目录，UI 也没有任何拦截。
* **实测证据**（真实方法、真实文件系统）：
  ```text
  CASE A:  before: ['Song1']   after: []   folder still there? False
  用户看到的消息仅：("complete", "复制完成: 成功 0, 失败 1 ...", 100)
  ——歌曲已经没了，界面却只报告"复制失败"。
  ```
* **建议替换**（新增统一入口，替换 2540-2559 整段）：
  ```python
  def _dir_size(self, path: str) -> int:
      return sum(os.path.getsize(os.path.join(r, f))
                 for r, _, fs in os.walk(path) for f in fs)

  def _safe_copy_song(self, src_path: str, dst_path: str) -> None:
      """校验同源/嵌套 → 备份式改名 → 失败回滚，绝不先删原目录。"""
      src = os.path.realpath(src_path)
      dst = os.path.realpath(dst_path)
      if src == dst:
          raise ValueError(f"源路径与目标路径相同，已中止（否则将删除源歌曲）：{src}")
      if dst.startswith(src + os.sep) or src.startswith(dst + os.sep):
          raise ValueError(f"源与目标互相嵌套，已中止：{src} -> {dst}")
      if not os.path.isdir(src):
          raise FileNotFoundError(f"源目录不存在：{src}")
      if not self._is_valid_song_root(os.path.dirname(dst)):
          raise ValueError(f"目标父目录不是有效的歌曲根目录，已中止：{dst_path}")

      backup = None
      if os.path.exists(dst):
          backup = f"{dst}.__backup__{datetime.now():%Y%m%d_%H%M%S}"
          os.replace(dst, backup)                  # 只改名，不删除，保证可回滚
      try:
          shutil.copytree(src, dst)
      except Exception:
          shutil.rmtree(dst, ignore_errors=True)   # 清掉半成品
          if backup:
              os.replace(backup, dst)              # 回滚原目录
          raise
      if backup:
          shutil.rmtree(backup, ignore_errors=True)
  ```
  并删除 2547-2556 的整段，改为 `self._safe_copy_song(src_path, dst_path)`。

### P0-2 目标目录已存在时被**无条件删除并覆盖**，且从不校验目标真的是 Quest

* **问题代码**：`shutil.rmtree(dst_path)`（2548-2550）
* **原因**：
  1. 同名文件夹在两端代表"同一首歌"是一个**未经验证的假设**。实测把一个 9999 字节的曲目覆盖成 4 字节，全程无提示、无备份。
  2. `validate_quest_path()`（1914-1951）**仅在 `select_folder` 里调用**；`copy_missing_to_quest` 全流程没有任何"目标确实是 Quest/CustomLevels"的复核。用户误把目标框设成 `D:\Beat Saber\CustomLevels`（本机主目录）时，程序会照删照拷。
  3. 帮助文档 3342/3347 行明确写着"**自动跳过已存在的歌曲**"，与代码行为完全相反 —— 用户会基于文档预期而放心点击。
* **实测证据**：
  ```text
  CASE B:  dst song.ogg size before: 9999  →  after: 4
           queue: ('complete', '复制完成: 成功 1, 失败 0', 100)
  ```
* **建议替换**（替换 2547-2559，并新增目标校验）：
  ```python
  # 复制前（_copy_missing_songs 内，2474 行之后）：
  if os.path.realpath(source_path) == os.path.realpath(target_path):

  if target == "Quest" and not self.validate_quest_path(target_path):

  if os.path.exists(dst_path):
  ```

### P0-3 `execute_delete` 没有"路径必须位于歌曲根目录之内"的约束，且在主线程执行

* **行号**：2652-2664（尤其 **2663** `shutil.rmtree(base_path)`）、2630-2632
* **问题代码**：
  ```python
  shutil.rmtree(base_path)          # 2663
  ```
* **原因**：
  1. 唯一的防线是 `if not base_path or not os.path.exists(base_path)`（2630）。当路径变量为空时 `os.path.join("", song_name)` 返回**相对路径**，`rmtree` 会相对当前工作目录删除 —— 实测复现（CASE C）。
  2. 没有校验 `base_path` 是 `local_path_var/quest_path_var` 的**直接子目录**，也没有 `realpath` 归一化，符号链接/`..`/手工编辑输入框都能让删除越界。
  3. `rmtree` 在 **UI 主线程**同步执行（2663），删除 Quest 上数百 MB 的曲目时整个界面冻结，Windows 上还可能出现"无响应"。
* **实测证据**：
  ```text
  CASE C:  os.path.join('', 'RelativeSong') == 'RelativeSong'
           execute_delete('RelativeSong', 'RelativeSong', 'local') → folder still exists? False
  ```
* **建议替换**（整体替换 `execute_delete` 2661-2670 前半段）：
  ```python
  def execute_delete(self, song_name: str, base_path: str, list_type: str) -> None:
      root = self.quest_path_var.get() if list_type == "quest" else self.local_path_var.get()
      root_real = os.path.realpath(root) if root else ""
      target = os.path.realpath(base_path)
      if not root_real or not os.path.isdir(root_real):
          self.show_error("歌曲根目录未设置或不存在，已中止删除"); return
      if os.path.dirname(target) != root_real:            # 必须是根目录的直接子项
          self.show_error(f"拒绝删除根目录之外的路径：\n{target}"); return
      if not os.path.isdir(target) or os.path.islink(target):
          self.show_error(f"路径不是普通目录，已中止：\n{target}"); return
      threading.Thread(target=self._delete_worker, args=(song_name, target, list_type),
                       name=f"Delete_{song_name}", daemon=True).start()

  def _delete_worker(self, song_name: str, target: str, list_type: str) -> None:
      try:
          shutil.rmtree(target)
          self.progress_queue.put(("ui_call", lambda: self._after_delete(song_name, list_type), 100))
      except Exception as e:
          logger.error("删除失败 %s: %s", target, e, exc_info=True)
          self.progress_queue.put(("error", f"删除失败: {e}", 100))
  ```
  `execute_delete` 里 2670-2703 的列表清理逻辑原样搬进 `_after_delete`。

### P0-4 搜索框每敲一个字重建整个列表：1000 首 ≈ **6 秒/键**，2000 首 ≈ 15.5 秒

* **行号**：186（`trace`）→ 397-405（`_filter_songs`）→ 284-293（`_display_songs`）→ 299-341（`_create_song_item`）
* **问题代码**：
  ```python
  self.search_var.trace("w", lambda *args: self._filter_songs())     # 186
  ...
  self._display_songs()                                             # 405（每次按键全量重建）
  ```
* **原因**：没有任何**虚拟化/分页/去抖**。每首歌创建 4 个真实 Tk 控件（实测 2000 首 = 8001 个控件），且 `_display_songs` 在每次按键、每次排序、每次对比后都被同步调用。搜索时用户每输入一个字符就同步重建 N 个控件，事件循环完全阻塞。
* **实测证据**：
  | 歌曲数 | Tk 控件数 | `_display_songs()` 耗时 |
  |---|---|---|
  | 200 | 801 | 1.54 s |
  | 1000 | 4001 | 6.68 s |
  | 2000 | 8001 | **15.48 s** |
  | 1000 首连敲 5 个字符 | — | **29.82 s（5965 ms/键）** |

  目标场景（Beat Saber 曲库 1000~3000 首）下，程序在输入搜索词时表现为**完全假死**，Windows 会弹出"程序未响应"。
* **建议替换**（去抖 + 分页，两处改动）：
  ```python
  # 1) SelectableListBox.__init__ 里新增
  self._search_job = None
  self._page_size = 200
  self._page = 0

  # 2) 替换 186 行（同时修掉 trace 弃用，见 P3-6）
  self.search_var.trace_add("write", self._on_search_changed)

  def _on_search_changed(self, *_args) -> None:
      if self._search_job:
          self.after_cancel(self._search_job)
      self._search_job = self.after(250, self._filter_songs)     # 250ms 去抖

  # 3) 替换 284-293，改为分页渲染
  def _display_songs(self) -> None:
      self._search_job = None
      for w in self.content_frame.winfo_children():
          w.destroy()
      self.item_widgets = []
      total = len(self.filtered_songs)
      pages = max(1, -(-total // self._page_size))
      self._page = min(self._page, pages - 1)
      start = self._page * self._page_size
      for i in range(start, min(start + self._page_size, total)):
          self._create_song_item(i, self.filtered_songs[i])
      self.page_label.configure(text=f"{start + 1}-{min(start + self._page_size, total)} / {total}")
      if self.item_widgets:
          self._select_item(start)
  ```
  > 更彻底的做法是把列表换成 `ttk.Treeview`（原生虚拟化，10 万行也不卡）；分页只是最小改动方案。

  ```python
  def _copy_via_adb(self, src: str, dst_dir: str) -> None:
      adb = shutil.which("adb")
      if not adb:
          raise RuntimeError("未找到 adb，无法直接向 Quest 写入；请改为先导出到本地目录")
  ```

### P2-3 每次调用都 connect/close，且无 WAL / busy_timeout

* **行号**：583、638、689、751、779、804、828
* **实测**：`journal_mode: delete`（未启用 WAL）；12 线程并发写入本机未复现 `database is locked`（负载太轻），但 MTP + 大曲库场景下超时风险真实存在。

  ```python

          conn = sqlite3.connect(self.db_path, timeout=10.0)
          conn.execute("PRAGMA journal_mode=WAL")
          conn.execute("PRAGMA synchronous=NORMAL")
          conn.execute("PRAGMA busy_timeout=10000")
          self._local.conn = conn
      return conn
  ```
  > 说明：当前代码**没有**触发 `check_same_thread` 报错，因为每个方法都在调用线程内新建连接。所以"跨线程共用连接"不是现存 bug；真正的隐患是"删库竞态（P1-6）+ 无 WAL/超时 + 无事务批处理"。
